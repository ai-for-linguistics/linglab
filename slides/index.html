1 / The idea

A matrix of tests

Rows are facts. Columns are theories.
Each cell records a test and its evidence: pass, fail, pending, out of scope.

Raw Facts is a distinguished theory: it is the stipulation of all facts. It passes all tests, by construction.

~60 s. Walk one row and one column. Take one row: a sentence and a verdict about it; some theories accept it, others do not. A theory whose language cannot say a sentence at all gets "out of scope", which is different from "failed". Pending means nobody has tested it yet. The first column, Raw Facts, is a distinguished theory: it passes every test, because it simply stipulates each fact. It is the baseline (all coverage, all complexity), and a check that the facts are consistent. Only two things add to the matrix: a new fact (row) or a new principle or theory (column).

3 / Research becomes visible

Proxies for Research

The Coverage vs Complexity plot lets you compare theories. You can switch between different metrics, all imperfect proxies for coverage and complexity.

A good theory passes many facts with few, simple principles.

Coverage: e.g. # successes, weighted successes
Complexity: e.g. # principles, compressed size of the Lean code

~60 s. Raw Facts has the highest coverage and the highest complexity: it is the baseline. A good theory sits near the frontier: nearly as much coverage, with far fewer principles. None of the measures is the truth: they are proxies for coverage and complexity, and they can disagree (in the earlier Anaphora work, code-size rankings in two proof assistants barely agreed). So each axis has a dropdown: coverage (facts passed, passed over applicable, confidence-weighted, with or without LLM judgments) and complexity (number of principles, with or without auxiliary ones, code length). Two side-by-side plots and a length table let you see whether the choice changes the story. Positions here are illustrative, not results.

Appendix / Honest evidence

Every result says how it was obtained

All evidence is stored, with its verification and model scope.

Lean and Python cross-check each other; disagreements are flagged.

~75 s. This is the honesty guardrail. A result can hold several pieces of evidence, and all of them are stored. Two scales apply. Evidence: a proof checked by a verifier (e.g., Lean) beats a simulation (e.g., Python), which beats what a paper claims. Verification: a person who checked the translation beats an LLM check, which beats none. The page shows the strongest evidence, and the verification status next to it. If entries disagree, you get a marker, never a block. Informal is never shown as formal. Weaker checks are skipped when a stronger one already passed, unless you ask. The order is a default; you can change it by prompting.
Appendix / The baseline

Raw Facts: the theory that just lists the facts

It is pure stipulation: the sum of all facts. It passes all tests, by construction, and is in principle the most complex theory. It also flags facts that duplicate or contradict each other.

~45 s. Raw Facts is a column like any other, built automatically from the fact list. It plays two roles. First, a check: every fact must be trivially provable there, so it catches facts that duplicate or contradict each other early. It does not check that a fact was translated into code correctly: that is the Translations tab (in the appendix). Second, a reference point: maximal coverage, maximal size. It is the point on the later plot that real theories must beat.
Appendix / The pieces

Facts and principles are small pieces of code

Each has words, quotes from papers, a confidence, and code the machine can run. A theory is a set of principles.

~60 s. The key move: a fact (a datum) and a principle (an assumption) are the same kind of object, a statement with code. Facts come from data, principles from theories. A theory is just a list of principles switched on. Principles are independent of any framework family; a bad combination simply breaks or scores poorly, and that is itself a result. You never need to read the code: the assistant writes it, and the page shows the statement in plain words. The code is what lets the cell be a real test.
Appendix / What you check

Cells are certified. The translation is not.

Check: Is the code statement faithful? An LLM wrote that translation. Review through an LLM, or ideally a person.

A Translations tab puts words next to code, for you to check.

Not convenient? Ask for another visual helper for this step.

~60 s. Be clear about what the machine does and does not guarantee. A cell is certified: a verifier (Lean) or a run (a simulation) produced pass or fail, and the page says which; a simulation is exact only for the models it covered, and the cell says so. What nobody certifies is the step before: that the statement in words was translated into code faithfully. An LLM wrote that translation, and an LLM can double-check it, often successfully, but a subtly wrong translation gives a certified but meaningless cell, and only a person checking by hand fully certifies the result. That is why every fact and principle is shown in words next to its code in the Translations tab, with a tick per row (kept in your browser only). You can also ask for a translation sheet, for the paper's own examples to be reproduced, or for an independent reviewer. If the default tab is not convenient, ask for another one: this is the critical manual step.
